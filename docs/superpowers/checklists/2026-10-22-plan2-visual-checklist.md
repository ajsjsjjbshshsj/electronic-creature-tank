## 0. 这份清单能证什么、不能证什么（方法学，先读这一节）

### 0.1 取证环境

| 项 | 事实 |
|---|---|
| 渲染面 | Qoder in-app Browser，`http://localhost:8123/`（`server.ps1 -Port 8123`） |
| 可见性 | `document.visibilityState === 'hidden'` ⇒ 真实 `requestAnimationFrame` **永远不触发** |
| 泵帧方式 | 把 `requestAnimationFrame` 换成"只记录回调"的桩，`boot()` 真 `src/main.js` 到一张离屏 canvas，然后手动以 `t += 16.7ms` 调用被记录的回调 |
| 视口 | 必须**手写** `viewport.width/height/dpr/scale` 与 `canvas.width/height`：hidden 页面零布局尺寸，`boot()` 自己的 `resize()` 会把 `canvas.width` 设成 0（这是本轮踩过的坑） |
| 世界 | 真内核：`createWorld` + `tickWorld` + `updateBodies` + `renderer.draw` + `consumeEvents`，一条都没桩替 |
| 结论适用范围 | "这套代码在这台开发机的 Chrome 里画出来的像素"。**不等于**任何真机的观感与帧时间 |

### 0.2 ⚠️ `canvas.toDataURL()` 只导出 canvas，不导出水

spec §3.4-5 与 §5.2 决定"canvas 透明叠加、水体渐变走 CSS `body` 背景"。于是**裸导出的 PNG 里，浏览器会显示深靛紫水体的地方是一片白**（控制方先前抓的 `01-`/`02-` 两张就是这种）。任何拿裸导出做的"对比度够不够""读不读得出来"的判断都是**可疑的**。

本轮所有 `10/20/30/40` 号段的全幅图都做了合成：先按 CSS 的三段色（`#0B0620 0% → #1A0B2E 55% → #2D1240 100%`）填一张等尺寸临时 canvas，再把真 canvas `drawImage` 上去，最后 `toDataURL`。裁切图（`zoom`/`panel`）从**同一张合成图**上取，所以裁出来的水体颜色与它在全幅里的位置一致，不是把渐变拉伸到裁切框上。

### 0.3 这套 harness 结构上证明不了的东西（诚实清单）

1. ~~**耳朵**：§5.4 的六声表、落地闷响、出词前那记「啾」的听感，本轮全部 未验证，一条都没验。~~
   ✅ **2026-10-22 控制方实听签掉（「声音没问题」）**。本 harness 确实测不到（没有音频设备 + `AudioContext` 只在真实手势栈里创建），
   所以这一格从一开始就是留给你的耳朵的。还剩三条没被逐条点名，见 §2.6。
2. **手指**：指针事件可以合成，但 `HAND_SPEED_POKE` 要的是"真人以正常速度划过会不会被读成粗糙"。合成轨迹是模型输出，B17 已如实记着（`src/behavior.js:61-104`）。本轮**没有**真手指。
3. **真实设备**：手机竖屏是用 `390×844 + dpr=3` 在桌面 Chrome 里**模拟**的。CSS 布局、字号与位图尺寸的关系是真的；**屏幕物理尺寸、视角、触控延迟、真机 GPU 不是**。
4. **真实时序**：帧间隔是喂进去的常数。"动画顺不顺、有没有卡顿感"这种判据本轮**结构上测不到** —— 只能报每帧耗时分布，不能报手感。
5. **"多久发生一次"**:凡是用写内核状态凑出来的画面，本清单标 **⚙️构造状态**。它证明"这种状态长这样"，**不证明**"它常发生"。

### 0.4 复现配方（照抄即可）

```js
// 1) 泵帧 harness（页面里执行一次）
const cbs = []; globalThis.__orig = globalThis.requestAnimationFrame;
globalThis.requestAnimationFrame = (cb) => (cbs.push(cb), cbs.length);
globalThis.cancelAnimationFrame = () => {};
const mod = await import('/src/main.js');            // 已被页面加载过，import 命中的是缓存
const cv  = document.createElement('canvas');
const ctrl = mod.boot({ canvas: cv, seed: 20261022, populationCap: 24 });
// 2) 手写视口（关键：boot 的 resize 把尺寸设成 0 了）
const v = mod.createViewport(900, 620, 1);           // scale 必须由它算，别手填
Object.assign(ctrl.viewport, v);
cv.width = 900; cv.height = 620;
// 3) 泵：调用**最后**一个被记录的回调（step() 每帧在开头重新注册自己）
let t = 0; const step = () => { t += 16.7; cbs[cbs.length - 1](t); };

// 想读 renderer 内部（气泡池 / bursts / time）就注入自己的 renderer：
const rnd = (await import('/src/render.js')).createRenderer({
  makeCanvas: (w, h) => { const o = document.createElement('canvas'); o.width = w; o.height = h;
                          return { ctx: o.getContext('2d'), surface: o }; },
  rng: (await import('/src/rng.js')).createRng(1), viewport: { ...v }, isMobile: false });
const origDraw = rnd.draw.bind(rnd);                 // 计时用包装，不改行为
rnd.draw = (c, w, b, vp, dt) => { const t0 = performance.now(); origDraw(c, w, b, vp, dt); drawMs.push(performance.now() - t0); };
const ctrl2 = mod.boot({ canvas: cv2, seed: 20261022, populationCap: 24, renderer: rnd });
// boot 内部的 resize 会 rnd.onResize(ctrl2.viewport, world.rng.fork())，所以静态层会按真视口重建一次
```

次数账单靠**包 `CanvasRenderingContext2D.prototype`** 得到（`drawImage / fillText / measureText / createLinearGradient / createRadialGradient / beginPath`），跑完必须还原原型与 `requestAnimationFrame`，否则后续会话继承一个被包的上下文。本轮结束时已还原并 `ctrl.stop()` + 刷新页面。

本清单各行的"复现"用到的四个自造 helper（都在页面里现搭，不进仓库）：

| helper | 干什么 |
|---|---|
| `comp()` | 按 0.2 的办法把 CSS 水体色合成到一张等尺寸临时 canvas 上，返回该 canvas（`shot` 与 `zoom`/`panel` 都从它取图） |
| `shot(name)` | `comp().toDataURL()` → POST 到 sink `:8124/save?name=…`，全幅导出 |
| `zoom(name, cx, cy, half, factor)` | 从 `comp()` 上按 CSS 坐标裁 `2·half` 见方、最近邻放大 `factor` 倍 |
| `panel(name, specs, half, factor)` | 多个 `zoom` 拼成一张横排多格图，每格上方用 `fillText` 写 harness 标签（**标签不是产品画面**） |
| `strip(name, track, n, every, half, factor)` | 每 `every` 帧调一次 `track()` 取当前跟随点，把那一帧的裁切拼成一条横向时序带（蹦跳、溶散这类"过程"用它） |

### 1.1 七种情绪的身体语言与体色，在无文字提示下是否可辨认

- **看什么**：只给身体（含眼睛、尾巴、碎边、体色），不给文字，能不能分出喜 / 怒 / 惧 / 困 / 卖萌 / 好奇 / 幸福。
- **怎么复现**：⚙️构造状态 —— 挑 8 只彼此距离 > 3× 体半径的个体（本轮 24 只缸里只找到 5 只够隔离），逐只写 `emotions.*` / `needs.*` / `memory.entries[PLAYER]` / `intent.kind`，然后按同一 `half` 裁切拼成一张多格图（`panel()`，格子上方那行小字是 harness 注的标签，不是产品的东西）。
- **看到什么**：`33-emotions-iso-A.png`（幸福 / 快乐^^ / 委屈 / 害怕，**已按"彼此距离 > 3× 体半径"筛过，是本轮最可靠的一格**）、`34-emotions-iso-B.png`（愤怒，同一轮里唯一够隔离的第 5 只）、`31-emotions-body-A.png`、`32-emotions-body-B.png`（**方法学次品**：没做隔离筛选，`31` 的第 3、4 格与 `32` 的第 7、8 格里有别的个体挤进来，只能当辅助证据）。
  - **快乐 ^^ 最清楚**：`33` 第 2 格两道上弯弧一眼可读。
  - **愤怒可读**，但读法是"脏/蛾"而不是"炸毛"：anger 把碎边换成蓬松那一档，画出来是身体一圈**灰白色毛刺**（`34` 里那只）。色相上它和"亮"没关系，所以第一眼的联想是"发霉"。
  - **害怕与委屈在参数上分得很开**（见 1.9），但在 12× 以下的实际尺寸里，害怕那一格读成"一条横带"而不是"两只瞪圆的小眼"（`35` 第 4 格）。
  - **幸福（星星眼）与好奇、卖萌三者在无文字下不易分**：卖萌 `pupil 0.95` + 腮红 `0.84`，好奇 `pupil 0.613` + 腮红 `0.40`，幸福是白圈里一颗深色四角星 —— 在 r≈14px 的个体上，三格都读成"两只大眼 + 一点粉"。
- **为什么自动化测不到**：记录型桩只数调用次数，不记参数值（`tests/render.test.js:23` 文件头就写着这条边界）。四参数与十行表的**数值**全部由 `tests/eyes.test.js` 钉住（896 条里那一支），但"这组数在 28px 的毛绒上读出来是哪一种情绪"是**感知判断**，没有任何断言能替代。

### 1.2 粉色生物在深靛紫背景上是否确实"像在发光"

- **看什么**：生物周围的水有没有被点亮；还是只有身体本身是亮的。
- **怎么复现**：`46-glow-ray-probe.png` 是裁切图；数字来自沿"体心 → +x"射线在**合成后**的图上取 9 个点（挑了 6× 半径内无同类、无食物的一只，hue 6.3、r=7.4px）。
- **看到什么**（亮度 L = 0.2126R+0.7152G+0.0722B）：

  | 距体心 | 0.5r（身内） | 0.78r | 1.06r | 1.34r | 1.62r | 1.90r | 14r（背景） |
  |---|---|---|---|---|---|---|---|
  | L | **110.6** | 20.1 | 17.2 | 16.1 | 14.9 | 14.9 | 13.6 |

  ⇒ **身体本身确实自亮**（核心 110.6 对背景 13.6，约 8 倍），这来自第 4 层体内亮区 + 第 2 层本体的明度档；但**体外那一圈光晕几乎不亮**：1.6–1.9r 处只有 +1.3 个亮度单位（+9.6%），肉眼不可见。真正能被看见的"发光感"来自 0.78–1.06r 的**碎边**（+48% / +26%），也就是 §4.7 那条"只画毛尖碎边"的决策顺手承担起了原本交给光晕的活。
- **判读**：**半通过**。"像在发光"成立，但成立的原因是"毛在发光"而不是"第 1 层光晕在发光"。`glowAlphaFactor 0.30` 那一层在当前 dpr=1 的导出里贡献 ≈ 0；若将来要"整只柔和地亮起来"，得动那一层而不是碎边。
- **为什么自动化测不到**：桩记不到 `fillStyle` / 渐变色值 / 像素亮度（`tests/render-body.test.js:605` 明确写着"混合模式写入次数是这三层存在的证据，桩记不到值，值进手工清单"）。本轮这条是**真像素测出来的**，但"够不够发光"仍是人眼判断。

### 1.3 竖屏手机上缸是否铺满、生物是否不畸形不过小

- **看什么**：390×844 下有没有黑边、生物有没有被拉扁、单只是否小到看不清是星。
- **怎么复现**：`H.mk(20261022, 390, 844, 3, true)`（isMobile=true ⇒ 微粒走 `CONFIG.particles.mobile`），`world.populationCap = 16`（⚙️手写，boot 的 coarse 判定在桌面 Chrome 下给的是 desktop），倍速 4× 泵 1400 帧到 t≈350 模拟秒、16 只满员，再切回 1× 泵到一个新鲜气泡。对照图 `39-phone-390x844-dpr1.png`（同种子同帧数、dpr=1）。
- **看到什么**：`30-phone-390x844-dpr3.png`（位图 1170×2532）。
  - 铺满：是。canvas 尺寸 = 视口尺寸，水体渐变铺到四边，无黑边。
  - 不畸形：是。`viewport.scale = 1.5`（`createViewport` 的 `scaleMin` 在 390 短边上生效），圆面积比与桌面同一档，没有椭圆化。
  - 不过小：**勉强**。个体直径 2r×scale ≈ 30–55 CSS px，在 390 宽里占 8–14% —— 星形轮廓认得出，但**眼睛已经糊成两个白点**（对照 `33` 的 6× 裁切才看得清表情）。
  - 附带问题：这一屏里 **39 份青绿光藻占了上半屏**，比 16 只生物显眼得多（见 O-2）。
- **为什么自动化测不到**：`tests/render.test.js:155` 钉住了 `createViewport` 的 clamp 行为、`:365` 钉住了手机走 `particles.mobile`。**"30px 的星在手机玻璃上认不认得出是星"没有任何断言能写** —— 它取决于物理尺寸、视角、屏幕素质。

### 1.4 两只社交时的脉动同步是否看得懂

- **看什么**：两只相处时，呼吸/亮区脉动会不会同相。
- **本轮结论**：**未验证，且当前无可验对象**。计划 2R 的 A2c 删掉了求偶结算与 `mated` 事件（spec §5.4.1 第 2 条同源），孤雌制下**没有"社交高峰"那一刻**；而 `body.phase` 由 id 哈希推出（`src/body.js` 的 `phaseOf`/`blinkInterval` 一族），两只的相位天生不同。

### 1.5 死亡的溶散是否足够温和（不惊悚）

- **看什么**：`dissolveT ≈ 0.45` 那一刻的样子；微粒是"上升消散"还是"炸开"。
- **怎么复现**：⚙️构造触发 —— 写 `victim.alive=false; victim.dying=1e-6; victim.deathHandled=false`，之后**走真管线**（`sim.js` 的死亡闸门发 `death` 事件 → `consumeEvents` 装微粒 → `reapDead` 累加 `dying` 到 4 秒后发 `dissolved`）。每帧查 `render.dissolveT(c)`，越过 0.45 那一帧导出。
- **看到什么**：`25-dissolve-mid-c.png`（全幅）、`26-dissolve-mid-zoom.png`（6×）。t=0.45（`dying=1.8s` / `CONFIG.dissolveDuration=4s`）时：星形轮廓**仍然完整可读**、体型已放大到约 1.4 倍、整体上浮、颜色退成暗紫褐、光晕先熄灭（`dissolveGlowPow 3` > `dissolveAlphaPow 2`，spec 那句"光慢慢熄灭 → 身体溶散"的顺序在画面上成立）。**读感：像一截烧尽的余烬，温和，不惊悚 ⇒ 通过。**
  - 但**微粒几乎看不见**：那一帧 `bursts.count = 11`（14 颗里已收走 3 颗），在 6× 裁切里只剩右侧三五个针尖大的点。"身体溶散成微粒上升消散"这一句，画面上**身体那半句成立、微粒那半句读不出来**。
- **为什么自动化测不到**：`tests/render-fx.test.js` 数得出粒子**个数**与调用序列（文件头第 29 行就承认"溶散看起来温和不惊悚，桩只数得出粒子个数"）。"上升消散 vs 炸开"是运动的气质，需要看。

### 1.6 Q 弹回弹是否自然而非抽搐

- **看什么**：落地那一刻压扁 → 过冲拉长 → 收回，有没有"弹一下"而不是"抖三抖"。
- **怎么复现**：`strip()` —— 等到一只 r>11 的个体进入 `hop`（p<0.04），之后每 3 帧裁一格拼成一条横向序列（裁切框**跟着抬升后的身体走**，所以这条带子显示的是形变而不是位移）。
- **看到什么**：`45-hop-strip-big.png`（12 格，`activity 0.76`、`minDuration 0.48s`）。每格上方标着当帧的 `p` 与 `squashV`：
  `p0.03 sq1.01 → p0.12 sq1.05 → p0.21 sq1.08 → p0.29 sq1.10 → p0.38 sq1.10 → p0.47 sq1.09 → p0.56 sq1.06 → p0.65 sq1.03 → p0.74 sq0.68 → p0.82 sq1.10 → p0.91 sq1.01`
  ⇒ 滞空拉长到 1.10、落地（`hopLandAt 0.72`）压到 0.68、**过冲回到 1.10 再收到 1.01**：一次过冲、不抖。`44-hop-strip.png` 是废片（挑到一只 r=3.4 的幼体且意图在采样前就换掉了，12 格全是 p0.00）。
- **判读**：数值形状与"自然"一致；**但"像不像 Q 弹"这句仍要真人看这条带子**，本轮只能保证它不是抽搐（过冲只发生一次）。
- **为什么自动化测不到**：`hopSquashAt` 的曲线由 `tests/render-fx.test.js` 逐段钉住（"轨迹五段的数值形状已测"）。桩看不见"抖几下"这种时间上的气质。

### 1.7 边缘那圈读起来是"毛"还是"光晕"（§4.7 那条决策的唯一判据）

- **看什么**：放大后边缘是一根根浅色毛尖，还是一圈均匀的雾。
- **怎么复现**：`H.zoom(name, cx, cy, r*2.1, 8)` —— 最近邻放大 8 倍，不插值。

### 2.6 B18 · §5.4 声音（**控制方实听签掉：「声音没问题」**）

> ✅ **2026-10-22 由控制方在真实浏览器里实听确认。** 这一条本来是本清单唯一**原理上无法自证**的一节：

> 连点击都被浏览器拒掉（`NATIVE_BROWSER_VIEWPORT_UNAVAILABLE`，面板不可见时视口是 0×0）。
> 所以"六声到底响没响、听着对不对"只有你的耳朵能签，而它签了。

**签掉的**：§5.4 六声表 + 落地闷响 + 出词前那记「啾」的**存在性与可听性**，以及"听着没问题"这个总判断。

**仍然开着的三条**（"没问题"是一句总签,没有逐条点名,所以按未答记；这三条各自都有明确的量法）：

1. **死亡那一声**响度只有 `death.peak = 0.12`、总线 `masterGain = 0.16`,spec 要的是"几乎听不见"——
   "几乎"与"完全"之间没有任何测试能分辨。要坐实：安静环境下只放第 7 声,问"听得到吗"。
2. **24 只一起叫会不会糊成一锅**：`maxVoices = 6` 只挡**同时发声数**,不挡混在一起的听感。
   要坐实：`__tank.setTimeScale(4)` 挂十分钟,听是不是噪音。
3. **不看屏幕能不能听出是哪一家的孩子**（§5.4 的核心承诺）。参数侧是真的：同一声"开心",
   size 14 的幼体是 1114→1671Hz、size 38 的大只是 411→616Hz；色相分 12 桶,倍音比从 2.020 走到 2.970。
   但"分得开"是听感,桩与参数都证不了。要坐实：随机点两只,背过身去猜大小。

**为什么自动化测不到（这一节的总说明）**：`tests/audio.test.js` 那 57 条用的是**记数值**的音频节点桩
（记频率、包络两端、波形、增益、start/stop 时刻、connect/disconnect 计数）。它能证明
"这里会送出一段 600→900Hz、0.085 秒的正弦、响两声",证不了"那听起来像不像『咐咐』"。
桩与耳朵之间没有桥,这是 Web Audio 这类程序化合成特有的形状 —— 也是为什么这一格必须由人来签。

### 3.3 对照 spec §5.3 的预算

预算是"桌面 24 只 60fps / 手机 16 只 60fps"⇒ 硬门槛 **16.67 ms/帧**。

- 桌面 1×：均值 3.52 ms = 预算的 **21%**；p95 5.5 ms = **33%**。
- 桌面 4×：均值 5.06 ms（**30%**），p95 9.4 ms（**56%**）—— 倍速把内核子步进乘了 4，绘制不变，符合预期。
- 手机模拟：均值 2.39 ms（**14%**），p95 3.8 ms。
- 最差时刻（溶散 + 两条气泡）绘制均值 2.44 ms、p95 4.2 ms ⇒ **没有哪一类事件把帧顶穿**。
- 三条硬约束（不每帧 `shadowBlur`、不每帧新建渐变、运行时不分配）在真浏览器里**逐条成立**（渐变 0/帧；`drawImage` 次数与桩测账单逐笔对得上，说明运行时没有偷偷多画）。

**⇒ 结论：达标，不需要动用降级顺序。** 降级顺序（① 手机端种群上限 16→12；② 小体型碎边降一档密度；③ 关闭光束摆动）**本轮一条都不启用**。

**必须挂在结论上的三条限制**（不然这段话会被当成手机实测）：
1. 全部数字来自**开发机 Chrome + 桌面 GPU**，手机模拟那条只证明了"在这个位图尺寸下逻辑撑得住"，**不等于中低端安卓机的 GPU/CPU**；真机至少按 3–5× 折。
2. 帧间隔是喂进去的常数，**测不出掉帧的手感**（0.3 节第 4 条）。
3. 最大值那一列（12–15.3 ms）出现在个别帧，本轮没做 profile 归因（候选：sprite 惰性缓存首次构建、GC）。它没有越过 16.67 ms 门槛，所以不构成待办；**若真机越过，先按 §5.3 的顺序砍，不要临场发挥**。

### F-1（视觉缺陷，中）：第 1 层光晕跨出 canvas 后失去"发光"效果
- **现象**：合成图上，身体外 1.6–1.9r 处亮度只比远背景高 1.3/255（+9.6%），肉眼不可见；"发光感"实际由碎边（+26%~+48%）承担。
- **机理**：`'lighter'` 只在 canvas 内部生效；canvas → 页面背景是普通 alpha 合成，而水体渐变根本不在 canvas 里（§3.4-5）。所以"用 additive 把光叠进水里"这条路在透明 canvas 的设计下**结构上不通**。
- **代码位置**：`src/render.js` 第 1 层（`glowRadiusFactor 1.75` / `glowAlphaFactor 0.30`）、`src/config.js` 的 `render.glow*`；背景侧 `css/main.css:17`。
- **最小复现**：泵帧后按 1.2 的射线取点亮度（或看 `46-glow-ray-probe.png`）。
- **影响**：spec §4.3"粉色生物像在发光"这条审美目标只兑现了一半。修法要么把水体搬进 canvas（推翻 §3.4-5），要么把光晕改成"提高自身 alpha 的浅色描边"（那是碎边的活）。**属设计裁定，不是改个常数的事。**

### F-8（交互缺陷，中）：第一次手势之前按的静音被整条丢掉，且第一次按下算的是"取消静音"

> ✅ **已修（2026-10-24，`176aa51`）**。空窗期由 `main.js` 持有一份 `muted`（`:885`），
> `unlockAudio` 建好叫声层后补写（`:906`）。判据 `boot：第一次手势**之前**按的静音不许丢`，

/ `state.bytes = …`，`main.js:679-680`），所以读到的一直是活的。**`hud.preload` 也是安全的** ——
`preloadList()`（计划 3 Task 2 写的）不是又一个"有生产者没消费者"：`hud.js:417` 把它挂到 api 上，
`main.js:1264` 在开缸时逐张交给一个游离 `<img>` 预热。查这两处是为了下一轮不必再查。
剩下的两个是真问题：

1. **第一次手势之前按的静音被整条丢掉。** 懒创建留了一段"`audio === null`"的空窗，而
   `setMuted` 原来是 `if (!audio) return true;` —— 请求不进任何地方。更糟的是
   `getMuted()` 在这段空窗里返回 `true`（含义是"听不见"），于是**第一次按下算的是
   `setMuted(false)`，也就是"取消静音"**，与按钮上"静音"两个字正好相反。
   ⇒ 玩家开缸第一件事就是点静音，然后在第一次点击缸体时被叫一声。
   修法：空窗期由 `main.js` 持有一份 `muted`（所有权写清楚：有音频时真相在 `audio` 里，
   没音频时这条请求就是真相），`unlockAudio` 建好叫声层后**补写**一次
   （`main.js:906`）。新判据 `boot：第一次手势**之前**按的静音不许丢`，探针（删掉那行补写）被抓到。
2. **`main.js` 承诺过一个不存在的消费者。** 原注释写"静音按钮在降级缸里也得能把按钮自己
   置灰，靠的是这个**返回值**而不是异常" —— 而 `pressMute` 从来没读过那个返回值，
   `getMuted()` 在 HUD 里只用来算反相。注释承诺的东西不见了，测试也看不见（桩里
   `getMuted: () => true` 是个只出不进的常量 ⇒ "按完之后字有没有变"这类断言**无从成立**）。
   修法：按钮文字跟着事实走（`静音` ⇄ `已静音`，与暂停键 `暂停` ⇄ `继续` 同形），
   桩改成**成对读写同一个变量**（与它自己第 62–64 行对 `getApiConfig/setApiConfig` 的要求同一条
   理由）。探针（删掉 `textContent` 那行）被抓到。

**记一笔还没修的**：设置面板那一行"新档/已存 · NNNB · 已写 N 次"的刷新时机是
**每一次控件交互**（`paintPanel()` 在 `setEndpoint/setModel/setKey/setSpeech/saveSettings/pressClear`
与开面板、确认态到期上都调，`hud.js:396`–`:566`），但**不骑帧**。所以面板开着、玩家不动任何东西时，
那串落盘代价就停在最后一次重绘那一刻。代价是一行会过期的读数，不是静默失败，本轮不动它；
要动就照左上读数那套"值变了才写"把它接进 `frame()`，别每帧无条件改 DOM。（见 §6 的 F-10）

### 11.2 机器侧证明（基线 1052 → 1089）

| 判据 | 为什么它必须是这个形状 |
